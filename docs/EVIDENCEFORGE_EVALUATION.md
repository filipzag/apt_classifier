# EvidenceForge Evaluation Report

## Overview

This report documents the evaluation of the APT Attribution Assistant's technique-mapping
pipeline against synthetic security data generated by
[EvidenceForge](https://github.com/Cisco-Talos/EvidenceForge) (Cisco-Talos). It measures
ATT&CK technique mapping only; no EvidenceForge bundle carries a threat-group label, so
group attribution is not evaluated here.

The regex cue tables (`_EXPLICIT_TECHNIQUE_CUES`, `technique_signals.SIGNALS`) cover 10 of 10
branch-office ground-truth techniques, 7 of 20 manufacturing techniques and 7 of 17 clinic
techniques. Performance tracks that coverage, which is the main reason the branch-office
numbers must not be read as generalization performance.

## Methodology

### Ground truth and leak resistance

The evaluator (`scripts/evidenceforge_eval.py`) reads ground-truth labels only for scoring.
`GROUND_TRUTH.activity`, scenario descriptions, ATT&CK annotations and any other
label-bearing prose are never placed in model input. Identical normalized inputs with
conflicting labels abort the run.

1. **narrative:** renders only the observable `attributes` of each GROUND_TRUTH event.
2. **windows:** selects native Windows Event XML records that match the event by exact host,
   event type, and at least one exact event-specific observable (command line, image,
   IP/port, logon type ...). A time window is only a bound, never the selection criterion.
3. **ecar:** the same exact alignment against native eCAR JSONL records.
4. **all:** runs the three modes separately and reports them separately.

Events that cannot be aligned exactly are reported as *unsupported* with a reason and
excluded from the case set. Coverage is therefore part of the result: a mode with high
precision on few scorable events is not better than a mode with lower precision on all of
them.

Both the application (`AttributionEngine.analyze`) and the evaluator go through the same
`AttributionEngine.map_techniques()` pipeline. `--pipeline local` disables OpenRouter
verification and is the hard quality gate; `--pipeline production` adds the LLM verifier and
is reported separately when run.

### Known limitations of the labels

- EvidenceForge technique annotations are **non-exhaustive intent labels**. A correct
  mapping of a behaviour the scenario author did not annotate (for example T1057 Process
  Discovery on a `tasklist` event) is counted as a false positive.
- Native-record modes are narrated by the repository's own Sysmon/eCAR phrasebook
  (`evidence/winlogs.py`, `evidence/ecar.py`); those numbers partly measure that
  phrasebook, which is also what production uses.
- Case counts are small (2 to 21 per mode), so the bootstrap intervals are wide. Treat the
  numbers as regression signals, not as absolute quality claims.

### Metrics

Canonical `evaluate_technique_predictions` metrics (exact and parent-aware P/R/F1,
hit@1/3/10, MRR, zero-label FPR) over the **accepted** technique set, with case-level
bootstrap 95% confidence intervals. Output files record scenario/ground-truth/bundle hashes,
generation seed, EvidenceForge commit, ATT&CK version, model revisions, preset and pipeline
fingerprint.

## Analysis

1. **Held-out narrative performance is low and red herrings are accepted.** On the clinic
   bundle narrative hit@1 is 0.22 and micro-F1 0.23. Two of the three benign red herrings are
   accepted (`cln-rh-001` as T1560.001 in all modes; `cln-rh-002` as T1036.005 in narrative
   mode, new since the acceptance model was enabled). These are the only zero-label false
   positives in the corpus and they occur only on the untuned bundle. No fix has been made
   in response, because any change motivated by a clinic failure would end its held-out
   status; the public held-out benchmark carries no zero-label cases, so this is the one
   place where over-acceptance is visible and it must be watched.
2. **Ranking is ahead of acceptance everywhere.** hit@10 is 0.59 to 0.80 in narrative mode
   while accepted-set F1 is 0.21 to 0.32: the correct technique is usually surfaced for
   review, but the local gate accepts at most one similarity-only candidate per observation.
3. **Native-record modes look better partly because of coverage selection.** Windows mode
   scores 2 of 11 branch-office events and 7 of 21 clinic events; the events that survive
   exact alignment are the ones with a distinctive command line or image, which are also the
   easiest to map.
4. **Development and held-out numbers diverge as expected.** Narrative hit@1 falls from 0.40
   (branch-office) to 0.24 (manufacturing) to 0.17 (clinic), in step with cue-table coverage.

## Recommendations

1. Keep `heldout-clinic` untouched. Any fix motivated by a clinic failure moves that bundle to
   development status; generate a new bundle before quoting generalization numbers again.
2. Use the public held-out benchmark (`make benchmark-public`, about 1,400 labelled cases) as
   the primary gate for gating and ranking changes; EvidenceForge bundles are regression
   signals with wide intervals.
3. Re-record the production run on the clinic bundle whenever the verifier prompt, model or
   scope changes (`scripts/evidenceforge_eval.py --pipeline production`).

## Reproduction

```bash
# 1. Clone and install EvidenceForge
git clone https://github.com/Cisco-Talos/EvidenceForge.git
cd EvidenceForge && uv sync

# 2. Generate the bundles (seeds as in the table above)
uv run eforge generate scenarios/branch-office-example/scenario.yaml -o /home/fzagar/evidenceforge_output --seed 42
uv run eforge generate /home/fzagar/apt_classifier/data/evidenceforge/heldout-manufacturing/scenario.yaml -o /home/fzagar/evidenceforge_heldout --seed 1337
uv run eforge generate /home/fzagar/apt_classifier/data/evidenceforge/heldout-clinic/scenario.yaml -o /home/fzagar/evidenceforge_clinic --seed 2024

# 3. Run all three local evaluations (requires ChromaDB with ingested ATT&CK data)
cd /home/fzagar/apt_classifier
make evidenceforge-eval-all

# 4. Compose the verification artifact
PYTHONPATH=. .venv/bin/python scripts/collect_verification.py
```
